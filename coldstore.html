The filler fetches 1-minute bars from the vendor, gzips them, and writes them straight to R2. Postgres sees only a progress row and a manifest row per tick — no bar writes, no bar scans. The statement timeout and connection ceilings that took the database down on 6 August simply stop applying, because the database is no longer in the path.

Object layout

Hive-partitioned gzip CSV, readable as one table by DuckDB over the S3 API. Columns are ts,open,high,low,close,volume with no header row — deliberately identical to what the earlier Postgres-side exporter wrote, so old and new objects read together.

tf1/ticker=<TICKER>/ym=<YYYY-MM>/part-<YYYYMMDD>-<YYYYMMDD>.csv.gz

A tick never straddles a calendar month, so every object sits under exactly one ym= prefix. The key is derived from the days inside it, so a re-run overwrites rather than duplicates. Every PUT is read back and byte-length compared before its manifest row is written — an object only counts here if it survived that check.

Legacy migration (Postgres → R2)

Paused, deliberately.

The original design wrote deep bars into Postgres and then dragged them back out to R2. That export drain saturated the instance on 6 August: the extraction call was running to its full 120-second timeout while a fresh invocation started every 60 seconds, so roughly nineteen ran at once, each holding a connection and a heavy table scan. Every other scheduled job starved behind it.

It is stopped in code and its schedule is removed. Nothing was deleted — the manifest still holds each chunk's true state, so it resumes exactly where it stopped once it has a single-flight lock, weekly rather than monthly windows, and a timeout short enough to fail fast. The bars it already moved are safe in R2 and counted below.
